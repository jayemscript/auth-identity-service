# V1 authentication and sessions

## Login and token verification

- `POST /v1/auth/login` accepts an email address or username and a password. Use Better Auth's server API for email sign-in and username-plugin sign-in, configured with Argon2id hash/verify callbacks. Resolve identifiers case-insensitively. Require an eligible account and an active grant for the calling app. Use a generic login failure for invalid credentials and ineligible accounts. Set a password length of 15–128 characters for new accounts and apply public entry-point throttling at the consuming backend. [Better Auth email/password](https://better-auth.com/docs/authentication/email-password), [username plugin](https://better-auth.com/docs/plugins/username), [NIST password guidance](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/)
- Each successful login creates a Better Auth PostgreSQL session in `auth.sessions` with app binding and V1 lifecycle fields, then returns its ID, access token, refresh token, and both expiry timestamps. Keep Better Auth's opaque session token internal. Count non-revoked sessions before their idle and hard deadlines for that user and app. Serialize the count and session insert with a database lock so simultaneous logins cannot exceed the cap. Return `409 SESSION_LIMIT_REACHED` when full and keep existing sessions. The BFF maintains one session per signed-in device or client context. V1 uses separate logins as the unit of concurrency.
- Sign both token types with HS256 using the deployment’s `JWT_SECRET`. Require distinct `typ` values, a fixed issuer, app ID as `aud`, user ID as `sub`, session ID as `sid`, and `iat` and `exp`. Add a generation number to refresh tokens. Fix the validation algorithm and require the expected token type on each operation. The service stores session IDs, user/app references, expiry, revocation state, and the current refresh generation. It stores neither issued tokens nor token hashes. [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html#section-3)
- `POST /v1/auth/verify` accepts `token` and `tokenType`. Validate the signature, claims, app binding, and current session, account, and grant state using PostgreSQL. For refresh tokens, verify the current generation as well. Return `active: false` for an unusable token and return `userId`, `appId`, `sessionId`, and `expiresAt` for an active one. Return `503` when state cannot be checked. Consumers use online verification for decisions requiring current revocation state.
- `POST /v1/auth/refresh` accepts a refresh token and runs the same validation inside a transaction. Increment the generation once and return the replacement pair after commit. A duplicate request using the prior refresh token fails while the replacement stays usable. The BFF serializes refresh per session and replaces the stored pair together. If the transaction commits but the BFF loses the response, the user signs in again, subject to the session limit.

## Session lifecycle

- At login, set the hard deadline from `JWT_REFRESH_EXPIRATION` and set the idle deadline from the effective app policy. Refresh extends idle time up to the hard deadline. Access verification is read-only. Cap access-token expiry at the earlier of its configured lifetime and the session deadlines. Refresh tokens expire at the session’s idle deadline, bounded by its hard deadline.
- `GET /v1/sessions` and `GET /v1/sessions/{sessionId}` use the caller’s access token and expose only that user’s sessions for the calling app. List active sessions by default, with an optional status filter and pagination. Return session ID, status, creation time, last refresh time, and deadlines. Expiry is evaluated from the deadlines on each call. Defer device identification and automated cleanup.
- `DELETE /v1/sessions/{sessionId}` revokes one owned session. `DELETE /v1/sessions` revokes all of the caller’s sessions in that app. `POST /v1/auth/logout` revokes the session in the presented access token. The BFF clears its stored pair once logout succeeds or once it confirms the session has ended. A caller who has lost every usable token can ask the SuperAdmin to revoke a session or wait for expiry.
- Keep SuperAdmin read and revoke operations available by target user and app at `/v1/admin/apps/{appId}/users/{userId}/sessions`, with `/{sessionId}` for a single session. These operations require the designated app and its live SuperAdmin token. After revocation commits, both token types fail verification and refresh for that session.
