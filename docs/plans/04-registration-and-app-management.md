# V1 registration and app management

## Registration

- `POST /v1/registration/public` requires an authenticated app with `registration.mode = public`. Accept name, email, password, and optional username and phone. When verification is off, create the account with `emailVerified: false`. When it is on, require a backend-supplied `verifiedEmail` matching the normalized registration email. The BFF must verify ownership before submitting the request and must derive the assertion from its completed verification flow. Missing or mismatched proof rejects the request before any insert. Store the verified flag and timestamp from the accepted assertion.
- `POST /v1/registration/internal` requires a live access token for an actor in the calling app and `can_create_users = true` on that actor’s current config. The consumer decides whether the actor may onboard the particular person. The identity service enforces the actor flag and app mode. `public` allows both routes, `operator_only` allows the internal route, and `disabled` allows neither. Internal accounts start unverified. Record the actor and source app from authenticated context.
- Both routes call Better Auth sign-up with automatic sign-in disabled, creating canonical records in `identity.users` and `identity.accounts`, then create the user config and app grant in the same PostgreSQL transaction. Configure Better Auth's Argon2id callbacks and username plugin. Return `201` with the user ID and let the caller log in explicitly afterward. Enforce case-insensitive unique email and optional username in PostgreSQL. Map Better Auth duplicate errors and database conflicts to `409` and create no grant, including when the email already exists through another app. Use the explicit grant flow to give that existing user access. Login sessions and verification proofs are stored in `auth.sessions` and `auth.verifications`.

Public registration creates one automatic grant for the registering app with source `registration` and no granting user. Internal account creation records the actor as the grantor. Do not automatically grant access to every registered app. Existing identities receive additional app grants through the explicit operator flow or seed, with source `operator` or `seed`; `granted_by_user_id` remains null when no operator granted access. Business profiles and roles such as merchant, customer, and courier belong to the consuming application.

## App management and access

Each consuming backend uses an app-bound credential from `apps.application_credentials`, sent as `X-API-Key: <credential-id>.<secret>` with the matching `X-App-Id`. Store only a SHA-256 hash of the random secret, return the secret once during CLI issuance, and check route scopes in the API key guard. Keep the shared `API_KEY` for `/health` only. Issue replacement credentials before revoking the old key. Credential scopes authorize calls to this identity service and do not represent business roles.

- The SuperAdmin can list apps at `/v1/admin/apps` and read one at `/v1/admin/apps/{appId}`. App records are deployment-owned and append-only: bootstrap may insert a new app, while the API and database reject app updates and deletes. Keep each slug stable because consumers send it in `X-App-Id`; add a new slug instead of changing an existing app identity. The designated admin app and its SuperAdmin grant remain protected.
- Use `PUT` and `DELETE` at `/v1/admin/apps/{appId}/users/{userId}/access` to grant and revoke access. Keep one grant per user-app pair. Use `PATCH /v1/admin/users/{userId}/config` for `canCreateUsers` and the nullable session limit override. Registration requests cannot set administrative fields.
- Revoke affected sessions in the same transaction as a grant revocation. Coordinate the writes with login and refresh so they cannot leave a usable session after access is removed. App rows cannot be disabled through the V1 API.
- `POST /v1/app-access/check` accepts a known `userId` from an authenticated backend and returns `allowed` for its own app, based on current account eligibility and grant state. The caller handles permission checks for its business actions. Unknown or disabled calling apps are rejected before processing the request.
